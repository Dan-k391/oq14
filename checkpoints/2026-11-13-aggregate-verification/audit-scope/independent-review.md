# Independent aggregate verification review

Reviewed the current scripts `tmp/aggregate_fresh_build.py`, `tmp/extend_aggregate_inventory.py`, `tmp/audit_all_project_constants.py` and `tmp/AllProjectAxiomAuditProbe.lean`, together with the retained stage 113 fresh build and historical stage 111 declaration audit, on 13 November 2026. This was an evidence, source and script review; no fresh aggregate rebuild was performed.

## Findings and exact scope

1. The stage 113 fresh compiler build is successful but is **not warning-free**. The 14 recorded diagnostics are nonsemantic linter warnings in historical sources: `ModalAlgebra` (9), `ModalWronskian` (3), `ScalarRadiation` (1), and `ModalDipole` (1). The build script records warnings but does not reject them. Describe the aggregate as successful with those 14 historical warnings. Do not modify frozen historical sources merely to change this wording; if warning-free aggregate output is required, treat a source change and its full dependent rebuild as a new reviewed replacement.
2. The complete all-safe-constant audit retained here is stage 111, not stage 113: 2,054 modules, 23,064 kernel-safe declarations, and 1,434 listed unsafe implementation roots excluded. Its own result, generated source, raw log, and archived stage 111 source-inventory and build metadata hashes match. Its allowlist is exactly `propext`, `Classical.choice`, and `Quot.sound`. Stage 112–113 additions, and subsequent final additions, need a fresh matching-stage safe-constant audit before a claim of all-safe coverage for the final ledger.
3. The build and declaration-audit tools use cached package and Lean runtime objects. They exclude the local project build directory from their recorded `LEAN_PATH`, instead prepending the retained fresh aggregate object directory. This supports the stated **fresh project** build, not a from-source build of Lean or mathlib. The evidence does not itself hash every package object or the Lean executable: for stronger binary provenance, record hashes of the compiler and external package artifacts (or otherwise authenticate their distribution) and state explicitly that package compilation is outside the aggregate.
4. The inventory extension discovers a local dependency only if its local `.lean` file currently exists; it does not itself reject an absent project import, authenticate a ledger source hash against the ledger entry, or verify a clean checkout before recording current source bytes. The present evidence independently passes the relevant checks below, so this is a guardrail weakness rather than a discovered bad dependency. Harden a future script by checking each root against its ledger `source_sha256`, rejecting unknown imports except an explicit trusted package/Lean namespace set, and authenticating tracked source bytes against the named commit or requiring a clean project-source checkout. A parser based on Lean's import header would avoid relying on text line shape.
5. Four historical ledger counts include more reports than inline source `#print axioms` commands: `MaxwellCutoffCommutator` 9 ledger versus 6 inline, `MaxwellCurlCutoffSource` 6 versus 4, `FlatLocalCurlSources` 2 versus 1, and `NestedCurlCutoffSource` 3 versus 1. Thus 10,821 is the aggregate's direct source-inline report count; it should not be presented as rerunning the extra historical external-driver reports. The complete all-safe declaration audit, once rerun for the final stage, also checks declarations without inline prints.

## Checks performed

- The stage 113 ledger file SHA-256 agrees with the inventory; all 1,508 ledger roots agree in order, and all their ledger source hashes match inventory. All 2,093 inventory source hashes match the actual files. The tracked `lean/` tree has no modification relative to HEAD at this check.
- All 2,093 fresh-build records have exit code zero, and all retained object and raw-log hashes match. The record names equal the inventory names without duplicates, with 10,821 reported inline axiom reports.
- For each inventory source, the local import list reconstructed by the inventory script equals its recorded dependency list and precedes the importer in inventory order. No indented import lines were found in these sources. All 196 distinct imports with no local source have Lean, Mathlib, or established package namespaces; no unknown nonlocal project import was found. This is an observed-source check, not a proof that the textual parser handles all syntactically valid Lean headers.
- The recorded `LEAN_PATH` starts with the aggregate fresh object directory and omits `lean/.lake/build/lib/lean`; external package paths and the Lean runtime remain intentionally cached. The compiler is invoked directly via the selected Lean 4.19.0 executable.
- The root selector checks module ownership and `!ci.isUnsafe` across the whole environment, so private and unprinted kernel-safe declarations owned by included modules are selected. Unsafe declarations are listed separately. The collector is `Lean.CollectAxioms.collect`, applied without a dependency filter to the complete selected roots; its checked-environment traversal collects declaration types and values. Hence an unsafe or custom axiom reached by a safe root would not be excused by the root exclusion and would fail the standard-only allowlist.
- The retained first failed attempt reported `Equiv.symm._elambda_2`; the separately retained kind probe establishes that this helper is an unsafe axiom-shaped compiler implementation while `Equiv.symm` is a safe definition with no axiom dependencies. Excluding unsafe roots is a justified scope distinction for kernel-safe proofs, not a blanket allowance for unsafe dependencies. This audit makes no claim that excluded executable implementation declarations are safe to run.

## Limits

Hash consistency and successful direct compilation establish the recorded build and dependency evidence under the pinned/trusted Lean and package environment. They do not independently establish the mathematical sufficiency of theorem statements or prove all prose claims. The source/ledger comparison and the source-header checks above were carried out independently for the current stage 113 evidence and should be repeated at the final stage.
